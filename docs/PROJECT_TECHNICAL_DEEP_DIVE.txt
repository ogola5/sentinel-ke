3.2 Security/access model
File: backend/app/api/deps.py

- All routers are protected by require_api_key unless dev bypass toggles are enabled.
- Expected key is FRONTEND_API_KEY, fallback INGEST_API_KEY.
- In development with API_AUTH_OPTIONAL_DEV=true, missing key can be tolerated.

Consequence:
- Access failures should be 401, not 404. So current 404 issue is not primarily an auth failure.

3.3 Layer 1: Canonical ingestion pipeline
Files:
- backend/app/ingestion/router.py
- backend/app/ingestion/service.py
- backend/app/ledger/repository.py
- backend/app/ledger/models.py

Flow for each event:
1. Source API key resolved against source_registry (hash-verified).
2. Source active check.
3. In-memory per-source rate limit (demo-grade).
4. Event normalization + schema validation.
5. Pseudonymization of payload/anchors.
6. Anchor sanitization to avoid prefix corruption (e.g., person_h:person_h:x).
7. Deterministic event_hash computation.
8. Append-only insert to event_log + event_entity_index.
9. Audit trail insert to audit_log.
10. Best-effort side effects (only on accepted events):
   - OpenSearch indexing,
   - GraphDelta generation + graph_delta_log insert,
   - Kafka publish for event and graph delta topics.
11. Synchronous campaign signal extraction in dev path when accepted.

Core property:
- Postgres event_log is canonical source of truth.
- Everything else is projection/derived.

3.4 Layer 1 search/timeline APIs
File: backend/app/api/events.py

Implemented:
- GET /v1/events/search
  query_string + filters over OpenSearch.
- GET /v1/events/timeline
  date_histogram aggregation over occurred_at.
- GET /v1/events/{event_hash}
  direct event retrieval by OpenSearch doc id.

Legacy overlap:
File: backend/app/api/timeline.py also defines GET /v1/events/timeline.

This duplicate endpoint family is architectural debt and can create confusion in behavior expectations.

3.5 Layer 2: Graph projection model
Files:
- backend/app/graph/projector.py
- backend/app/graph/models.py
- backend/app/graph/repository.py
- backend/app/graph/neo4j_worker.py
- backend/app/graph/service.py
- backend/app/api/graph.py

Model:
- Canonical event -> deterministic GraphDelta (nodes+edges with evidence hashes).
- GraphDeltaLog in Postgres persists projection intents.
- Neo4j worker replays deltas using projection cursor.

Safety/quality characteristics:
- Strict allowlist for labels and edge types.
- Edge merge accumulates evidence and counts.
- Provenance always includes event_hash on relations.
- Neo4j is rebuildable from Postgres deltas.

Graph read APIs:
- GET /v1/graph/entity/{entity_key}
- GET /v1/graph/neighbors/{entity_key}
- GET /v1/graph/path?from=...&to=...
- GET /v1/graph/evidence/{event_hash}

3.6 Layer 3: Analytics and intelligence workers

- backend/app/analytics/layer3/ddos_alert_worker.py
- backend/app/analytics/layer3/vpn_cluster_worker.py
- backend/app/analytics/layer3/mule_campaign_worker.py

DDoS worker:

VPN/infra worker:

Mule campaign worker:
- detects transfer fan-in + cashout patterns,
- upserts campaign/campaign_entity/campaign_event,
- writes synthetic campaign graph deltas.

6) ROOT-CAUSE ANALYSIS OF THE CURRENT LOG BEHAVIOR
====================================================================
6.1 Why infra/clusters moved from 500 to 200
- code now includes schema compatibility patch + cluster_key field + response mapping.
- observed logs confirm success.

6.2 Why events endpoints still 404 despite route code existing
Most probable explanations (ordered by likelihood):

A) Runtime route map mismatch (stale process/image/reload path)
- Code has /v1/events/search and /v1/events/timeline.
- Runtime may still be serving an earlier route map.

B) Path conflict behavior with dynamic route in another runtime version
- If an older events.py ordered /{event_hash} before /search, /search can be captured as event_hash and return 404 event_not_found.
- Current file order is correct, but runtime may not match current file.

C) Inconsistent duplicate timeline router family
- /v1/events/timeline exists in two routers (events.py and timeline.py), which is avoidable ambiguity.
- Not enough alone to explain /search 404, but indicates route hygiene debt.

D) Proxy/runtime environment divergence across services
- frontend and backend containers may not reflect same code revision state at that moment.

What is unlikely:
- Auth failure (would be 401).
- OpenSearch query miss (would not typically emit plain route-level 404).

6.3 Why UI can appear "connected but wrong"
- In App.tsx, fetchBackendSnapshot is all-or-nothing Promise.all.
- If /events/search or /events/timeline fails, snapshot load throws.
- App then sets offline/demo-fallback label and keeps demo data.
- Simultaneously, operations snapshot has safe per-endpoint fallbacks, so parts of UI can still feel semi-live.

8) DATA LIFECYCLE NARRATIVE (END-TO-END)
====================================================================
1. A source submits canonical event with API key.
2. Backend validates, pseudonymizes, hashes, stores in Postgres event_log.
3. Same accepted event is indexed to OpenSearch (search/timeline).
4. Event is projected into GraphDelta and stored in graph_delta_log.
5. Neo4j worker replays deltas to maintain graph projection.
6. Layer-3 workers analyze windows and write derived intelligence rows:
   - ddos alerts,
   - infra clusters,
   - campaigns,
   - anomalies,
   - mitigations,
   - AI outputs,
   - economic integrity outputs.
7. Frontend polls backend APIs every 30s and maps rows into SOC screens.
8. Case/STIX export endpoints package campaign intelligence for sharing/legal workflows.

Core invariant:
- canonical truth is Postgres ledger;
- OpenSearch and Neo4j are derived views;
- workers enrich the same canonical timeline into decision artifacts.

9) HOW TO EXPLAIN THIS TO SOMEONE (READY-TO-USE SCRIPT)
====================================================================
"Sentinel-KE is a layered cyber-intelligence system. The backend ingests normalized events from multiple sources, stores them immutably in Postgres, and then projects that evidence into OpenSearch for fast search and into Neo4j for relationship analysis. On top of that, analytics workers generate alerts, campaigns, infrastructure clusters, and economic-integrity findings. The frontend is a 7-screen SOC console that consumes those APIs every 30 seconds. Right now, infrastructure clustering and most analytics routes are healthy, but the events search/timeline routes are still returning 404 at runtime, so parts of the UI can degrade into demo fallback. The graph screen is currently mostly static and not fully bound to live graph APIs, and the scenario-control endpoints exposed in the frontend are not implemented in backend routing yet. So the core pipeline exists and is substantial, but route hygiene and last-mile integration are the main blockers to fully consistent live operation."
